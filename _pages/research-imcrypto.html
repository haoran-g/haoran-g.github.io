IMCRYPTO
IMCRYPTO: An In-Memory Computing Fabric for AES Encryption and Decryption
Published in: IEEE Transactions on Very Large Scale Integration Systems (TVLSI), 2022
Authors: Dayane Reis, Haoran Geng, Michael Niemier, Xiaobo Sharon Hu
Background

AES encryption is the core of many security protocols, from TLS to Intel SGX memory protection. However, AES is fundamentally memory-bound: the SubBytes and MixColumns steps require table lookups that cause frequent cache misses, and moving data between memory and a dedicated co-processor dominates execution time. For 1 MB of plaintext, data transfer overhead adds 744.49 µs and 30.39 µJ — dwarfing the computation cost itself. Existing hardware accelerators achieve high throughput but require data to be transferred out of memory, exposing it on the memory bus and wasting bandwidth.

Design

IMCRYPTO places the AES pipeline directly inside the SRAM arrays, at the level of the last-level cache (LLC). The design is built around three components: (1) Compute-Enabled Memory (CEM) arrays with custom sense amplifiers that perform XOR/AND/OR/ADD between memory words without reading data out; (2) a LUT fabric using 9T RA/CAM arrays (256×8) that combines SubBytes and MixColumns in a single step for encryption, and InvSubBytes + AddRoundKey + InvMixColumns for decryption; (3) a bidirectional shifter for ShiftRows. A RISC-V controller with 18 custom instructions coordinates the pipeline and enables programmability for multiple AES modes and other ciphers.

IMCRYPTO achieves minimum 3.3× and maximum 223.1× throughput-per-area improvement over prior AES ASICs and IMC architectures. When including data transfer overhead for ASIC designs, IMCRYPTO is 1.2× faster with 19.7× better area and 257.7× lower power than the best competing ASIC, and 5.7× better ADPP. Throughput per area reaches its peak against the PCM-based IMC design, with a projected 5.3× additional ADPP improvement using FeFET technology.

Conclusion

IMCRYPTO demonstrates that compute-in-memory is highly effective for AES because the algorithm's structure maps naturally onto LUT-based in-SRAM operations. The design serves as the foundation for PPIMCE, which extends the same fabric to support full HE and GC workloads.
